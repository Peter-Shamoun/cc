### Amazon ECS on AWS Fargate
| | |
|---|---|
| Purpose in ClaimClarity | Runs all ClaimClarity compute as three task types, with no EC2 hosts: the **chat API service**, the **run worker service** and the **parser task**. |
| Talks to | **Chat API:** the ALB (inbound), Cognito signing keys, the run queue (send), the ClaimClarity bucket (conversations, run-event chunks, cancel flags, limits object), KMS. **Run worker:** the run queue (receive, delete), STS (AssumeRoleWithWebIdentity with the user's token), the ClaimClarity bucket (gold reads, chunks, answers, agent audit), KMS, Amazon Bedrock. **Parser task:** started by the launcher for one batch. It reads raw, writes lossless and gold under one customer's prefix, and publishes the views ([Parser task](../pages/14-parser-task.md)). All three use VPC endpoints for AWS APIs. |
| Permissions | **Task execution role** (all three): pull its own image from ECR, write its own log group. **Chat API task role:** send to the run queue. It holds no customer data permissions of its own: S3 and KMS calls use the signed-in user's session credentials (Customer B's role, tagged with the user). **Run worker task role:** receive and delete on the run queue, sts:AssumeRoleWithWebIdentity, Bedrock InvokeModel for Claude Haiku only. Data access uses Customer B's role from the token ([gates 5 and 6](../pages/22-token-to-credentials.md)). **Parser task role:** Customer B's parser role, passed by the launcher ([gate 2](../pages/13-parse-trigger.md)). |
| Encryption | Ephemeral task storage encrypted by Fargate. All traffic is TLS. Data at rest is in S3 under SSE-KMS with the customer's key. Message text is also sealed with the per-user data key. |
| Data held / PHI | Chat API: PHI in memory only while a request runs, plus temporary chats (1 hour idle, at most 20 per user). Run worker: PHI in memory for one run. The DuckDB session has no temp directory, so nothing is spilled to disk. Parser: one batch in memory and in task storage, gone when the task ends. |
| Scaling and limits | **Chat API:** at least 2 tasks across two Availability Zones. Scales on CPU and request count. One process per task. **Run worker:** scales on queue depth per task (target 1 message per task). One run per worker at a time. Run deadline 110 s, inside the 120 s stop timeout. **Parser:** one task per batch, sized per batch type. Rolling deploys keep at least 100 % healthy, with the circuit breaker and rollback on. |
| Failure behaviour | **Chat API:** an unhealthy task leaves the target group, and clients reconnect to another task and replay from S3. **Run worker:** a run is not retried (the queue's maximum receive count is 1, then the dead-letter queue). Its stream stops, the client reloads, and the user retries. **Parser:** a failed batch is quarantined and alarmed. |
| Logging and audit | Each service logs to its own CloudWatch log group through the redaction filter, with no PHI. Audit events carry ids, counts and timings. The run worker writes one agent-audit record per SQL call under the customer's prefix. ECS API calls are recorded in CloudTrail. |

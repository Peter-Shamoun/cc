Where CC's design stands

This is my understanding of the current design, pieced together from the repo: the schema in claude/schema/, the data-backend canvas, the chat notes, the build-week plan and the project memory. Every claim has an ID so you can correct it by number.

How to correct me Reply with IDs and the fix, e.g. "B4 wrong: the API runs on Fargate" or "S6 is decided: we keep Neo4j for payer search." Chips show how settled I think each claim is: Built Designed Open Conflict
01 · The product

What it is

  1. P1Built
    CC is a chat analyst for Xifin's implementations team. It answers questions over a customer's 837P claims and 835 remittances so the team can size up a new customer before pitch and conversion conversations.
  2. P2Built
    It is an internal pilot in dev and not deployed to end users. Only LabCorp data is loaded. The rule since Oct 16 is "build for many customers, heading to production."
  3. P3Designed
    The target is a hosted, multi-tenant service with strict PHI boundaries, formally deployed by Thu Oct 29.
  4. P4Built
    The app code lives in another repo (main @ ca5df10). This repo holds only the design, data model, diagrams, tooling and research.

Simplified redraw of diagrams/data-backend-canvas/Main.dc.html, which stays the source of truth. Shown for customer B; every customer gets the same setup.

  1. B1Designed
    One prod S3 bucket with a cc/ prefix and one folder per customer. Each folder has its own SSE-KMS key and IAM role, and a bucket policy denies cross-prefix access. Tenant isolation is physical, so data tables have no tenant column.
  2. B2Designed
    The SFTP-to-S3 copy reuses LabCorp's existing IT script. It writes raw/received_date=…/ plus a _SUCCESS manifest (file list and sha256). Bronze is never edited.
  3. B3Designed
    The S3 event and EventBridge rule start a short-lived ECS Fargate task per customer batch. It runs as that customer's role, then exits and its credentials expire. There is no EC2 instance per customer, and the launcher only has iam:PassRole.
  4. B4Designed
    Files are parsed one at a time, and any file whose sha256 is already in edi.source_file is skipped. Writes go to staging/<run_id>/. Promotion into parquet/ and the semantic-layer rebuild happen once per batch. Bad files go to quarantine/.
  5. B5Designed
    The view SQL lives in GitHub (placeholder path semantic/views/). Only the parser runs it, to materialize every sem.* view into semantic_layer/v=<run_id>/, then it flips CURRENT. DuckDB reads only the materialized Parquet and never the SQL.
  6. B6Designed
    Parquet files are only ever added, never edited, at about one new file per table per day. There is no compaction job for now. If one is added later, it compacts within a partition and never touches bronze.
  7. B7Designed
    Read path: Entra ID login, then a Cognito JWT. The customer comes from Entra group membership (e.g. CC-LABCORP). The API verifies the token and gets 15-minute STS credentials for that customer's role, with SourceIdentity set to the user.
  8. B8Designed
    The API runs on EC2 and embeds DuckDB. Each request opens a fresh in-memory connection with an S3 secret scoped to that customer's prefix and lock_configuration = true, and closes it afterwards.This conflicts with the ADRs; see S5.
  9. B9Designed
    Claude is called through Bedrock under a BAA, with invocation logging off or kept inside the PHI boundary.
  10. B10Open
    Logging: CloudTrail S3 data events and KMS logs go to a separate Object-Lock log bucket and are queried with Athena. The recommended app audit log would hold the question, SQL, tables and row counts, but no result data. Whether to keep chat transcripts at all (and for 30 to 90 days if so) is undecided, and retention needs compliance sign-off.
  11. B11Open
    277 files arrive later and are not part of the first build.

  1. D1Built
    Silver is lossless at two levels. edi.segment can rebuild files byte for byte, and the typed tables are lossless at the element level, with each row pointing back to its seg_ord. Rare segments go to edi.misc_segment. Every file carries its S3 provenance.
  2. D2Built
    A PCN is not a key. Surrogate keys are file_id:seg_ord, and "current adjudication" is computed from event order. The dedupe in sem_int.remit_event is the fix for the Oct 20 load failure (8,294 duplicate keys in keys.remittances).
  3. D3Built
    Gold is the 10 sem.* views: remit_claims, remit_lines, claims, claim_lines, adjustments, remarks, payments, provider_adjustments, diagnoses, payers. They contain no patient names, member IDs, DOBs or bank accounts.
  4. D4Built
    The denial definitions are unchanged. A recorded denial is CLP02 = 4. A signal-v3 denial is a non-reversal 835 with $0 paid and CO-group CAS in the reviewed CARC list. "Denied" means either one. Rates grouped by CPT need at least 20 owners by default.
  5. D5Built
    Business rules live in views and ref.* config (denial_carc, tenant_setting, payer_alias), so they can change without a reload. "Built" here means DDL plus a synthetic DuckDB test that passes in CI. Nothing has been loaded with real data yet.
  6. D6Open
    Still to do: the X12 → Parquet parser (the plan is to port it from Appeals), loading ref.denial_carc with the 23 reviewed CARCs, populating payer_alias, and deciding how source_file supersession works when Parquet is append-only (rewrite each batch, or a separate log table).

  1. A1Built
    Today no query is written by the model on the live path. The Investigator picks typed tasks, the server compiles them, and the Writer writes prose only. Every number in the answer is bound by the server.
  2. A2Built
    A payer resolves without the user only on an exact match or a single normalized match. Otherwise the turn pauses on a payer card, and resuming reruns the stored tasks with no new Investigator call.
  3. A3Designed
    The bet: the agent works from the semantic layer about 90% of the time and loads the lossless schema only when it truly needs to. We accept less data completeness in exchange for accuracy, based on dbt's 2026 benchmark (98.2% through a semantic layer vs 90.0% with text-to-SQL for Sonnet 4.6).
  4. A4Open
    Moving the agent onto query_metrics over sem.* is scheduled in the build-week plan but not done. I'm not sure whether it replaces the Investigator's typed tasks or becomes a new task type inside run_tasks.
  5. A5Open
    Lane 2 (ADR-009): P2a is merged (PR #21) but unreachable, and P2b hasn't started. The silver views it needs, and widening the SQL guard to allow them, are not built.
  6. A6Open
    Whether the Payer Resolver makes an AI call. The diagrams label it "(AI)", but the aggregate describes lexical, vector and initials search.
05 · Decisions and blockers

What's unsettled

  1. S1Conflict
    ADR-010 (Accepted: central DuckDB on EC2 over Quack) vs ADR-011 (Proposed: interim two-EC2 dev, long-term ECS Fargate with embedded DuckDB). ADR-010 stands until you accept 011.
  2. S2Conflict
    The data-backend canvas draws a third option: DuckDB embedded in an EC2 API server, a new connection per request. This matches neither ADR exactly, and it needs to be settled before Terraform.
  3. S3Open
    Governance: Cognito approval is waiting on the CoE (10/19). DuckDB, Quack and SQLite aren't in the XiFin AI Standard Platform catalog. The DEV PHI-bucket policy is undecided, and so is whether LabCorp PHI files can be processed locally at all.
  4. S4Open
    Neo4j's future. DuckDB mode still uses Neo4j for payer search. Either host Neo4j, or move payer search to ref.payer_alias + sem.payers and drop Neo4j.
  5. S5Open
    Chat logs and telemetry: none are assumed for now, but it's undecided (see B10).
  6. S6Open
    Diagram housekeeping: Lucid still rejects the draw.io imports, and the turn-flow SVGs still say "Payer Resolver (AI)".

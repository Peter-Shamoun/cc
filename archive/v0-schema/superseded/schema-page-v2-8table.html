CC Schema v1

Eight tables. Two for what was billed, four for what was paid and why, one for code meanings, one for the source files. Every claim and remit row carries its exact EDI segments and their position in the S3 file, so nothing from the source is lost and the tables only model what people actually ask about.

The whole schema

file                     one per S3 object (837 or 835)
 ├── claim                one per CLM          (837)
 │    └── claim_line      one per SV1 line
 └── payment              one per check / EFT  (835 batch: BPR + TRN)
      ├── remit           one per CLP          ── claim_id      → claim
      │    └── remit_line one per SVC          ── claim_line_id → claim_line
      └── adjustment      one per CAS reason or PLB reason, at line, claim or payment level

code                     every code meaning: CARC, RARC, status, POS, frequency, PLB …

The 837 side and the 835 side each have a header, a claim and a line. The only extra table is adjustment, because a remit line can have many reasons and denial analysis is mostly "sum dollars by reason". The matched 837 claim is a column on remit, not a separate table.

Conventions

<table>_idPrimary key. The same name is used as the foreign key, so JOIN remit USING (claim_id) just works.
patient_control_numberCLM01 on the 837 and CLP01 on the 835. Same name on both sides.
_amountDECIMAL(18,2), signed as sent. Reversals are negative, so SUM(paid_amount) nets them out automatically.
_codeAlways text. Look up the meaning in code.
VARCHAR[]Used only for short repeated values (diagnoses, modifiers, remark codes). Filter with list_contains(col, 'X').
start_segment / end_segment / raw_ediWhere the row sits in the parsed file, and its exact segments. The lossless escape hatch.

How it stays lossless

  • file.s3_uri points to the original file and file.parsed_s3_uri to the parsed copy. Both are immutable.
  • Every claim, remit and payment row stores start_segment and end_segment into the parsed file, like your START_INDEX / END_INDEX.
  • The same rows also store raw_edi: the exact segment text. A claim's raw_edi includes the billing provider, subscriber and patient segments above it, so one row is a self-contained mini 837.
  • When a question needs a field we did not type out, the agent can still search raw_edi (for example raw_edi LIKE '%PWK*%') without a schema change. If a field gets asked for often, promote it to a column.

What the agent writes

Most questions need one or two tables.

S3 layout per tenant

s3://xifin-cc-<env>/tenants/labcorp/
  landing/                     original 837 / 835 files (immutable)
  parsed/                      parsed copies that start_segment / end_segment point into
  warehouse/v1/
    file/
    claim/        submitted_month=2026-10/   claim_line uses the same partition
    payment/      payment_month=2026-10/     remit, remit_line, adjustment use the same partition
    code/
  catalog.duckdb               COMMENT ON for every column; only sees this tenant's prefix

Each customer gets the same tree under its own prefix with IAM scoped to it. Month partitions are copied onto child tables so one date filter prunes the whole join.

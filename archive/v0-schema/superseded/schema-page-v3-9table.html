ClaimClarity · Labcorp · 837P + 835 · one copy per tenant

ClaimClarity Schema v1

Nine tables that follow the files' own shape: file, batch, claim, service line on each side, plus two adjustment tables on the 835 side. The 837 and 835 sides are built the same way, every join is a straight parent-to-child chain, and each claim and remit row points to its exact segments in the parsed file so nothing is lost.

Conventions

<table>_idPrimary key, generated by the pipeline. The same name is used as the foreign key, so JOIN … USING (remit_id) works.
patient_control_numberCLM01 on the 837 and CLP01 on the 835. Same name on both sides.
_amountDECIMAL(18,2), signed as sent. Reversals are negative, so SUM(paid_amount) nets them. Positive adjustment amounts mean less money paid.
copied columnspayer_name, payment_date and trace_number are copied down from the batch so most questions skip a join.
VARCHAR[]Only for short repeats: diagnoses, modifiers, remark codes. Filter with list_contains(col, 'X').
start_index / end_indexWhere the row sits in the parsed file (file.parsed_s3_uri). Anything not in a column can be read from there.

S3 layout per tenant

s3://xifin-claimclarity-<env>/tenants/labcorp/
  landing/                       original 837 / 835 files (immutable)
  parsed/                        parsed copies that start_index / end_index point into
  warehouse/v1/
    file/
    claim_batch/  claim/  claim_service_line/            partitioned by submitted_month
    remit_batch/  remit/  remit_service_line/
    remit_adjustment/  remit_batch_adjustment/           partitioned by payment_month
  catalog.duckdb                 COMMENT ON for every column; only sees this tenant's prefix

Each customer gets the same tree under its own prefix, with access scoped to it. Child tables carry the parent's month column so one date filter prunes the whole join.

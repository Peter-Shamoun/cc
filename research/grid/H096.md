## How factors were run
- candidates3: three distinct SQL drafts per question (A direct, B CTE-decomposed, C alternative formulation) were all executed. The pick was the majority result; with no agreement, the generation-style candidate won (direct→A, decompose_cte→B, metric_spec→C).
- fewshot: TF-IDF retrieval of the 3 nearest non-dev, non-heldout questions from another family, with their gold SQL (listed in each result's `trace`). The drafts were changed only where the examples showed a convention (q11/q12 denial rate as a fraction rounded to 4 places; primary taken as DISTINCT claim_key, payer_key). No fixes driven by errors.
- explore: 1–5 profiling probes per question were run before the final SQL and counted in sql_execs.
- verifier: a critic pass on empty or all-null results, with one revision to an alternative candidate.
- repair: up to 2 repairs. The first rewrites the SQL from the DuckDB error message (quotes and aliases a reserved word); the second falls back to the next candidate.
- assumptions: the chosen interpretation was recorded per question. It did not change the SQL.
- multiagent: a planner pass (spec) handed to a separate SQL-writer pass in one executor. These were not true subagents.

## Caveats
- One analyst (Grok Bot) drafted the candidate library once for all five cells, so the cells are not independent samples of the drafting step. Differences between cells come only from how the factors are executed.
- The 20-day snapshot has no August payment data, so the July-vs-August questions are close to degenerate.

# Grid cell C001

Config: `generation=direct_sql`, `fewshot=1`, `explore=1`, `candidates3=1`, `verifier=1`, `repair=1`, `assumptions=1`, `multiagent=1`. Model: Grok 4.7.

Dataset `98e61f03e594` (generator 3.3, the benchmark test scenario: 20 days, volume scale 0.3, seed 5). Queries ran through a non-escalated `open_snapshot` reader, the same sandbox `bench/eval_subagents.py` uses, and the guard's 1000-row limit.

Dev set: all benchmark questions except the 27 `heldout_hard_1` questions and anything tagged `grokbot-r1` (nothing is tagged). Sorted by `sha256(question_id)` and the first 20 were taken. n = 20.

Method: a shared profile of `sem.*` (distinct values, ranges, null rates, join cardinalities) was taken before any final SQL. For each question the planner froze the population, grain, date basis, units, and tie break. The SQL writer, using that plan plus the three BM25-nearest solved questions from outside the dev set (same parametric family and the held-out 27 excluded), wrote three direct SQL candidates. All three were executed. The majority result was kept; candidate A was in the majority on every question. A critic pass checked grain, primary-payer definition (`payer_responsibility = 'P'`, not 835 `payer_sequence`), denial versus zero-pay, and rounding, and did not rewrite. No chosen result was an error or empty, so repairs stayed at 0. Three candidate executions are counted per question; the shared profile is not.

Accuracy is recorded in `C001.json` after the deterministic matcher (`bench.compare.match` on the guard-reexecuted final SQL).

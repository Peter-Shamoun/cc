# Grid cell C008

Config: `generation=metric_spec`, `fewshot=1`, `explore=1`, `candidates3=1`, `verifier=0`, `repair=0`, `assumptions=1`, `multiagent=1`.

Model: grok-4.7. Dataset: generator 3.3, smallest benchmark scenario (20 days, volume scale 0.3, seed 5), snapshot `98e61f03e594`, non-escalated `sem.*` reader.

Dev set: every benchmark question except the 27 `heldout_hard_1` questions and anything tagged `grokbot-r1` (none in this tree), ordered by `sha256(question_id)`, first 20. n=20.

## Method

A planner subagent wrote a metric spec (metric, population, filters, grain, time window, ties, rounding) and stated the revenue-cycle interpretation. A separate SQL-writer subagent saw only that plan and emitted three structurally different DuckDB queries. All three were executed. Every question agreed 3/3, so the first candidate was kept. There was no critic pass and no repair.

Few-shot examples were the three BM25-nearest solved questions outside the dev set, excluding the same parametric family and the held-out 27. Explore probes covered distinct payer classes and names, date ranges, frequency codes, null rates, and join cardinalities before the spec was written.

## Scoring

Answers were committed before comparison. Scoring used `bench.compare.match` on the same snapshot, re-executing each submitted query and the question's gold SQL. SQL was not changed after that comparison.

Accuracy: **20/20**. Mean SQL executions per question: 8 (5 shared explore probes counted on each question, plus 3 candidate executions). Repairs: 0.

## Failure modes

None. All 20 dev questions matched the checker. Every question's three candidates agreed before the checker was consulted, so the kept SQL is the first candidate rather than a repaired query.
